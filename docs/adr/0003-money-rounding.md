# ADR 0003: Гроші та округлення

- Статус: прийнято
- Дата: 2026-11-20

## Контекст

Комісії та збори дають дробові значення копійок. Розбіжності округлення між продавцем, платформою і звітами недопустимі.

## Рішення

1. Тип грошей: `Money` на основі `BigDecimal` зі scale 2, валюта UAH. Тип відсотка: `Percent` зі scale 2, діапазон 0..100.
2. Режим округлення: HALF_UP (від нуля). Приклади: 0.005 -> 0.01, 0.004 -> 0.00, 3.5% від 1234.56 = 43.2096 -> 43.21.
3. Відсоток від суми: `round(amount x percent / 100, 2, HALF_UP)`.
4. Округлення **по кожному рядку замовлення окремо**; підсумок комісії є сумою округлених рядків і НЕ округлюється повторно. Приклад: рядки 16.6665, 19.999, 0.808 дають 16.67 + 20.00 + 0.81 = 37.48, тоді як округлення суми 37.4735 дало б 37.47.
5. Повернення комісії дорівнює збереженій комісії замовлення, а не перерахунку.
6. Зберігання в БД: `NUMERIC(19,2)` для грошей, `NUMERIC(5,2)` для відсотків. У JPA використовуються `AttributeConverter`.
7. Порівняння в коді через `compareTo`, не через `BigDecimal.equals`. `Money.equals` безпечний, бо scale завжди 2.
8. Знімки ставок (комісія категорії, ставка комісії платежу) зберігаються в замовленні та платежі, щоб пізніші зміни тарифів не змінювали минулі операції.

## Наслідки

- Плюси: передбачувані копійки, прозорі тести з конкретними числами, відповідність рядкам у документі замовлення.
- Мінуси: сума комісій за рядками може відрізнятися на копійки від «комісії від загальної суми». Це прийнято і задокументовано.

## Розглянуті альтернативи

- Зберігати копійки як `long`: відхилено, бо відсотки і проміжні значення все одно дробові.
- Банківське округлення (HALF_EVEN): відхилено, бо HALF_UP очікуваніше для користувачів.
- Округлення лише підсумку: відхилено, бо рядки в документі не збігаються з підсумком.
