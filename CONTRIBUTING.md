# Правила внеску

Дякуємо, що допомагаєте проєкту. Це короткий посібник: як працювати з гілками, комітами, PR та тестами.

## 1. Перед початком роботи

1. Візьміть issue зі стовпця Ready на дошці (або створіть його за шаблоном).
2. Перевірте [Definition of Ready](docs/scrum/definition-of-ready.md): є користувацька історія, критерії приймання, оцінка, мітки.
3. Призначте issue на себе і перенесіть у In progress.

## 2. Гілки

Формат: `<тип>/<номер-issue>-<короткий-опис-латиницею>`.

| Префікс | Коли |
|---|---|
| `feature/` | нова функціональність |
| `fix/` | виправлення помилки |
| `chore/` | збірка, залежності, CI |
| `docs/` | документація |
| `spike/` | дослідження з обмеженим часом |

Приклади: `feature/10-ad-campaign`, `fix/42-commission-rounding`, `docs/3-scrum-base`.
Від `main` гілку створюємо і в `main` повертаємо через PR. Прямі коміти в `main` заборонені.

## 3. Коміти (Conventional Commits)

Формат: `<тип>(<модуль>): <опис у наказовому способі>`. Типи: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`, `build`.
Модулі (scope): `common`, `seller`, `billing`, `subscription`, `catalog`, `advertising`, `order`, `payment`, `web`, `infra`, `docs`.
У тілі або в кінці: `Refs #N`. Приклади:

```text
feat(billing): add idempotent top-up posting

Refs #6
```

```text
fix(order): refund exact commission on cancel

Refs #11
```

## 4. Pull Request

1. Заголовок PR за Conventional Commits. Для зміни, що завершує issue, у описі: `Closes #N`.
2. Заповніть шаблон PR: що змінено, як перевірено, чек-ліст.
3. CI (`./mvnw -B verify`) має бути зеленим.
4. Потрібен хоча б один рецензент (у соло-режимі: самоперевірка за чек-листом і пауза перед злиттям).
5. Спосіб злиття: **squash merge**. Заголовок squash-коміту дорівнює заголовку PR.
6. Гілку після злиття видаляємо.

## 5. Тести і якість

- Кожна зміна бізнес-логіки має тести. Формули грошей (округлення, комісії, комісія за платіж) тестуємо параметризованими тестами з конкретними числами.
- Повний прогін: `./mvnw -B verify`.
- Тест `ArchitectureTest` охороняє межі модулів. Дозволені залежності:

| модуль | може залежати від |
|---|---|
| seller | common |
| billing | common, (seller: лише `SellerRegisteredEvent`) |
| subscription | billing, common, (seller: лише `SellerRegisteredEvent`) |
| catalog | subscription, common |
| advertising | catalog, subscription, billing, common |
| order | catalog, subscription, billing, common |
| payment | order, subscription, billing, common |
| web | усі модулі (лише сервіси і DTO, без репозиторіїв і сутностей), common; ніхто не залежить від web |

- Кожна сторінка інтерфейсу має тест `MockMvc` (дивись `src/test/java/ua/marketplace/web`); рядки з апострофом у тестах пишіть як `\u2019`, суми будуйте через `Html.uah(...)`.
- Зміни схеми БД: тільки новою міграцією Flyway `V{n}__опис.sql`. Уже застосовані міграції не редагуємо.

## 6. Правила коду

- Java 21, без Lombok. DTO оформлюємо як `record`.
- Гроші: лише `Money`, відсотки: лише `Percent`. Округлення HALF_UP до 2 знаків для кожного рядка окремо.
- Час: тільки через `Clock`, без `Instant.now()`.
- Ін'єкція залежностей лише через конструктор.
- Помилки: `BusinessRuleException` або `NotFoundException` з кодом `ErrorCode`.
- Форматування: `.editorconfig` (відступ 4 пробіли для Java, 2 для YAML/JSON).

## 7. Мова

Документація, issues і коментарі до задач: українською. Код, імена класів, коміти: англійською.
У документах не використовуйте довге тире (символ U+2014): замінюйте його двокрапкою, комою або дефісом «-». Також уникайте слова, що починається на «цен» і закінчується на «тр» (замінюйте на «ядро», «головний»).

## 8. Безпека

- Не комітьте паролі, токени, `.env`.
- Застосунок поки без автентифікації: не розгортайте його публічно.
- Про вразливості повідомляйте приватно власнику репозиторію, не через публічний issue.
